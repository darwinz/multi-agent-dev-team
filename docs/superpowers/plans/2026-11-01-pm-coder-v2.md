# Multi-Agent System v2.0 (PM → Coder) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a Product Manager agent in front of the v1 Coder inside one LangGraph graph, with a typed shared state, a JSON handoff, consolidation down to 8 tasks that keeps every requirement covered, a `team` CLI, and a demo API that passes a Postman-style fixture (rubric C2.1–C2.6).

**Architecture:** A new outer `StateGraph` over `ProjectState` runs `pm_node → (consolidate_node) → dispatch_node → coder_node ⟲ → finalize`. `coder_node` renders the Coder prompt from the `TaskHandoff` alone and runs the unchanged v1 `CoderAgent` in-process, forwarding its step events through the stream writer. A `TeamRunner` holds the workspace lock for the whole project, streams the graph, and writes evidence JSON after each step. The `team` CLI renders that stream.

**Tech Stack:** Python 3.12, uv, LangGraph 1.2.x, `langchain` `init_chat_model` + `with_structured_output`, Pydantic v2, rich, FastAPI + uvicorn + httpx, pytest.

**Spec:** `docs/superpowers/specs/2026-10-29-pm-coder-v2-design.md`. Read it in full before Task 1. Section numbers below (§5 etc.) refer to it.

## Review Focus

These five inputs are implied by the spec but not exercised by any task's main tests. Each has a test added to the task that owns the code.

1. **The PM returns a `covers` id that doesn't exist, or leaves a criterion uncovered, twice.** Expected: run status `failed` with a readable `error`, no Coder call, exit code 1. Test in Task 5 (`test_pm_failure_skips_coder`).
2. **The model's merge reuses an original id twice or drops one.** Expected: rejected, deterministic fallback used, `method="deterministic"`. Test in Task 3.
3. **A Coder provider error mid-project** (the Coder model raises). Expected: that task is `failed` with `coder_status="error"`, later tasks still run, run status `partial`. Test in Task 5.
4. **The generated app module can't import, or never binds its port.** Expected: `check_api` reports one failing line naming the startup error within its timeout, never hangs, and kills the server process. Test in Task 7.
5. **`team` started while another `coder`/`team` run holds the lock.** Expected: exit 2 with "workspace busy", and no `.coder/runs/<id>/` directory is created. Test in Task 6.

  - Node functions are built inside `build_team_graph`, with the names from Global Constraints.

Node contracts (§§4–8):
- **`pm_node`:**
  - On success, returns `spec`, `tasks=spec.tasks` and `task_status`, which holds a pending `TaskRecord` for every task, plus a `work_in_progress` line.
  - On `PMError`, returns `error` and `status="failed"`.
- **`route_after_pm`:** returns `finalize` if `error` is set or there are no tasks, `consolidate_node` if `len(tasks) > MAX_TASKS`, and `dispatch_node` otherwise.
- **`consolidate_node`:** returns `tasks`, `consolidation`, a `task_status` reset to pending for the new ids, and a progress line.
  - *Ruling (plan):* `task_status` is a merge reducer, so the original ids' pending records stay alongside the merged ones. `finalize` and the CLI therefore judge only ids in `tasks`. This keeps the reducer append-only, as C2.2 requires.
- **`dispatch_node`:** returns `handoff=make_handoff(state)`, sets `task_status[id].status="in_progress"`, and adds a progress line. `prior_files` is `sorted(state["code_output"])`.
- **`coder_node`:**
  - Reads only `state["handoff"]`. It must not read `spec`, `tasks` or `requirement`.
  - Runs `deps.coder.stream(render_task(h), lock_held=True)` and writes each event to `get_stream_writer()` as `TeamEvent(kind="coder", task_id=h.task_id, data=event.model_dump()).model_dump()`.
  - Returns:
    - a `task_status` record (`done` if the `CoderResult` status is `success`, `failed` otherwise, plus `coder_status`, `run_id`, `iterations`, `sorted(files)` and `summary=explanation[:500]`);
    - a `[TaskArtifact]`;
    - `code_output=result.files`;
    - `current_task_index + 1`;
    - `handoff=None`;
    - a progress line.
- **`route_after_coder`:** returns `dispatch_node` while `current_task_index < len(tasks)`, and `finalize` otherwise.
- **`finalize`:** sets status:
  - `failed` if `error` is set;
  - otherwise `completed` if every id in `tasks` is `done`;
  - otherwise `partial`.
- `render_task` lays out, in order:
  1. `Project: {spec_name}` and its description.
  2. `Task {task_id} ({position} of {total}, {priority} priority): {title}`.
  3. The description.
  4. `Acceptance criteria:` with `- [ ] ` lines.
  5. `Files from earlier tasks:` (or `none yet`).
  6. The instruction to build on those files, keep earlier tests passing, and run all tests before finishing.

### Task 6: TeamRunner: one lock per project, evidence files

**Files:**
- Create: `orchestration/team_runner.py`
- Test: `tests/test_team_runner.py`

**Interfaces:**
- Consumes: `build_team_graph`, `TeamDeps`, `TeamEvent`, `state_to_jsonable`.
- Produces `class TeamRunner`, with these members:
  - `__init__(self, settings: Settings, *, pm: PMAgent | None = None, coder: CoderAgent | None = None)`.
  - `stream(self, requirement: str, *, api_check: Callable[[Path], tuple[bool, str]] | None = None) -> Iterator[TeamEvent]`. `api_check` receives the workspace dir and returns `(passed, report_text)`.
  - `run(self, requirement: str) -> dict`, which returns the final state as jsonable.
  - `reset_memory(self) -> None`, which delegates to the Coder.
  - The attributes `run_dir: Path | None` and `final_state: dict | None`.
- `TeamEvent.kind` widens to `Literal["start", "spec", "consolidation", "handoff", "coder", "task_done", "final", "progress"]`.
- **Lock order.** `stream` takes `RunLock(settings.state_dir)` **before** creating the run directory. Only then does it create `.coder/runs/<run_id>/` (`run_id = uuid4().hex[:12]`) and emit `start` with `{"run_id", "run_dir"}`.
- **Graph stream.** It streams the graph with `["updates", "custom", "values"]`. The `recursion_limit` is `4 * MAX_TASKS + 10`.
- **Events and evidence files, per update:**

| Update | Event emitted | Evidence file |
|---|---|---|
| `pm_node` | `spec` (spec dump, or `{"error"}` on failure) | `state-after-pm.json` (current full values) |
| `consolidate_node` | `consolidation` | `consolidation.json` |
| `dispatch_node` | `handoff` | `handoff-<id>.json` (exactly `TaskHandoff.model_dump_json(indent=2)`) |
| `coder_node` | `task_done` (the `TaskRecord`) | `state-after-<id>.json` |
| `custom` chunks | passed through as `TeamEvent` | none |

- **Run start and end.** `requirement.txt` is written at start. At the end, **still holding the lock**, the runner does three things:
  1. If `api_check` is given and the status isn't `failed`, it calls `api_check(settings.workspace_dir)` and writes the report to `api-check.txt`.
  2. It writes `final-state.json`.
  3. It emits `final` with `{"state": …, "api_check": {"passed", "report"} | None}`.
  The lock is released only after that, so the check and the evidence describe the same workspace (from review).
- **Snapshots wait for post-step values (from review).** LangGraph emits a step's `updates` chunk **before** that step's `values` chunk. This was probed on 2026-11-01 and the order was `values{x:0}`, `updates{a}`, `values{x:1}`. So the latest `values` at update time is still the previous step's state.
  - On an update, emit the event and queue the snapshot filename.
  - Write every queued snapshot from the next `values` chunk.
  - `handoff-<id>.json` doesn't wait, because it is written from the update's own `handoff`.
  - The content assertions in `test_state_after_pm_has_tasks_but_no_progress` and `test_before_after_handoff` are the acceptance tests for this ordering.

|---|---|---|
| `health` | GET `{{baseUrl}}/health` | 200 `{"status":"ok"}` |

  6. Only **after** the process is reaped, read diagnostics:
     - on timeout or early exit, `seek(0)` the log and return one failed `CheckResult(name="startup", …)` whose detail is the last 20 lines of the log;
     - the detail also says whether the process exited or timed out.
